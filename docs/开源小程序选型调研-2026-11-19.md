# 潘小兜：开源小程序选型调研

调研日期：2026-11-19。范围：公开 GitHub 仓库的 README、许可证、目录、部分业务源码及提交记录；未部署候选项目、未做支付验收或完整安全审计。结论针对当前公开分支，商业版、插件版不能自动视为公开版自带能力。

## 结论

有值得参考的源码，但本次核查的 6 个候选中，没有找到能直接覆盖潘小兜全部经营规则、又无需明显改造的完整替代品。

**建议继续使用现有项目，以 bee 的餐饮点餐交互、CRMEB 的管理与售后流程作为完善参考。** 现有项目已经围绕批次预约、会员门槛、推荐奖励和退款冲正实现了专门逻辑，整体替换要重新移植并验收这些能力，不能只比较界面或功能数量。

若决定重新选底座：优先评估 CRMEB 当前 Apache-2.0 公开版；如果更看重餐饮收银、会员运营，也可评估 fuint，但先明确各模块授权以及公开版和付费版边界。bee 更适合参考或改造前端，原仓库没有可自托管后台。

## 当前需求基线

按当前 README 和已确认规则判断，而非沿用早期产品评估中尚未修复的问题：

- 单店卤味预订，每天 16:30 一批、16:00 截单、可预约次日。
- 按日期批次控制菜品库存和接单名额，汇总备餐数量。
- 店主自送、配送范围、到店自提及取餐码核销。
- 累计有效现金货款满 68 元入会，下一单享逐商品会员价；退款回退相应累计金额。
- 积分、单层推荐红包仅抵货款；推荐奖励在订单完成后可用，不可提现。
- 退款冲回奖励，已花掉的部分通过后续同类奖励抵回。
- 手机掌柜后台，覆盖商品、订单、批次、售后、资产流水和日报。
- 当前是原生微信小程序 + TypeScript/Node/Koa + MySQL，重视部署费用和本机模拟支付联调。

### bee：最接近点餐体验，但要分清前端与后台

根目录是小程序代码；`config.js` 配置 `subDomain`，会员页通过 `apifm-wxapi` 调接口。README 的运行步骤要求注册 api工厂后台并配置微信和支付。

因此，“免费前端源码”不等于“完整后台免费自托管”。若用它对接当前后端，需要处理商品规格、购物车、登录、结算、支付结果、履约状态、售后和会员字段的映射。其“在线订座”配置指向预约报名，不能当作已支持每日卤味批次。

适合参考：分类点餐、商品选购、取餐入口、自提核销、订单展示。实际复制代码时按 Mulan PSL v2 保留声明；商品图片、品牌和第三方素材分别核对。

证据：[README](https://github.com/woniudiancang/bee/blob/master/README.md)、[LICENSE](https://github.com/woniudiancang/bee/blob/master/LICENSE)、[config.js](https://github.com/woniudiancang/bee/blob/master/config.js)、[会员页接口调用](https://github.com/woniudiancang/bee/blob/master/pages/member-center/index.js)。

### CRMEB：最值得评估的完整商城底座

本次核查的是默认 `v8.0.0` 分支，不能套用旧版本文章中的技术栈或收费结论。当前仓库包含后端、管理端、uni-app、数据库安装材料；运行说明要求 PHP 8.2–8.4、MySQL 8 和生产 Redis，并包含队列、定时任务及长连接进程，运维组件比现有 Node/MySQL 多。

已查源码确认存在配送和核销相关处理、会员购买处理器、佣金冻结结构，以及订单退款赠积分冲正。值得注意：`OrderRefundRewardServices.php` 明确说明佣金冲正交由分销插件；赠积分不足部分记录后不再追扣未来积分。这不能直接满足潘小兜的推荐红包及后续奖励抵回规则。

适合参考：后台商品管理、订单工作台、售后时间线、资产明细、权限、页面装修。若整体采用，批次和资产规则仍应单独设计；先核对需要的分销等模块是否包含在所选公开版本中，以及插件是否收费。

证据：[README](https://github.com/crmeb/CRMEB/blob/v8.0.0/README.md)、[LICENSE](https://github.com/crmeb/CRMEB/blob/v8.0.0/LICENSE)、[配送处理](https://github.com/crmeb/CRMEB/blob/v8.0.0/backend/app/services/order/OrderDeliveryServices.php)、[会员交易](https://github.com/crmeb/CRMEB/blob/v8.0.0/backend/app/services/user/member/MemberTradeModeHandler.php)、[退款奖励冲正](https://github.com/crmeb/CRMEB/blob/v8.0.0/backend/app/services/order/OrderRefundRewardServices.php)。

### fuint：餐饮会员运营贴近，授权必须分模块看

仓库确实包含 Java 业务源码、Vue 管理端、uni-app、收银台及 SQL，不只是产品截图。后端 POM 使用 Spring Boot 3.2.12、Java 17；README 安装说明存在版本表述混杂，运行应以实际依赖验证。

不能简单标为“无许可证”，也不能直接标为“全套 Apache 免费闭源商用”：根目录没发现统一 LICENSE，但后端有 AGPL-3.0、uni-app 有 Apache-2.0，同时 README 要求商用购买授权。AGPL 本身允许商业使用，但涉及修改后网络服务的源码提供义务；若希望闭源运营，应先取得覆盖目标模块的明确商业授权。此处记录证据差异，不替作者推定授权范围。

适合参考：餐饮会员权益、收银、优惠券、积分流水、打印和门店运营。采用前应核实演示中的功能是否都在公开版。

证据：[README 使用范围](https://github.com/fushengqian/fuintCatering/blob/main/README.md)、[后端 AGPL](https://github.com/fushengqian/fuintCatering/blob/main/fuintBackend/LICENSE)、[小程序 Apache](https://github.com/fushengqian/fuintCatering/blob/main/fuintUniapp/LICENSE)、[预约服务源码](https://github.com/fushengqian/fuintCatering/blob/main/fuintBackend/fuint-application/src/main/java/com/fuint/common/service/impl/BookServiceImpl.java)。

### 另外三个候选为何不优先

- **litemall**：MIT 和完整多端代码是优势，但更偏标准商城。默认分支最近可见提交是 2025-10-05 的 README 调整，随后可见业务修复为 2025-06-19。仓库 2026 年的 pushed 时间不能直接当作核心代码持续更新的证据。来源：[提交记录](https://github.com/linlinjava/litemall/commits/master/)、[LICENSE](https://github.com/linlinjava/litemall/blob/master/LICENSE)。
- **bee-api**：确实有订单模型中的积分、退款、自提门店和核销码字段，但不能据此推定完整业务已验收。默认分支最新可见提交为 2026-03-12 的 README 调整；需核对缺失 `bee-region.sql` 和商用授权口径。来源：[README](https://github.com/cocktail18/bee-api)、[LICENSE](https://github.com/cocktail18/bee-api/blob/main/LICENSE)、[订单模型](https://github.com/cocktail18/bee-api/blob/main/bee-api/model/order.go)。
- **xcx-single-shop**：技术栈相近不能抵消老依赖、管理台缺失及支付改造工作。README 中商户配置还是 `Mch_key` 等旧接口形态，不可视为当前 API v3 可直接使用。来源：[README](https://github.com/lpbird/xcx-single-shop)、[LICENSE](https://github.com/lpbird/xcx-single-shop/blob/master/LICENSE)。

## 对当前建设路线的建议

1. **近期联调继续用当前项目。** 保留已经实现的批次库存、支付模拟、会员及奖励账本，集中打磨点餐、预约选择、支付后提示、取餐及掌柜待办体验。
2. **顾客端参考 bee。** 优先吸收菜单分类、规格选择、购物车、取餐入口的设计；如果选择替换前端，先适配“选菜—预约批次—结算—模拟支付—履约”一条链路，再扩展会员和售后。
3. **管理端参考 CRMEB，餐饮经营参考 fuint。** 主要借鉴信息组织和操作流程。PC 管理台不自动满足店主手机操作，需要单独检查移动端体验。
4. **只有明确要扩展通用商城、多端装修或复杂营销时，再评估整体换底座。** 独立目录部署验证，先跑批次容量争抢、满额入会、奖励收货结算、退款抵回等关键验收，再讨论数据迁移。

换源码不会解除微信测试号的限制，也不会替代正式小程序账号、商户绑定和支付配置。目前继续本机模拟支付，是独立于源码选型的有效联调路径。

本次只生成选型资料，未引入候选代码、未切换数据库、未改变正在运行的联调或云端环境。公开证据快照位于 `.runtime/research/open-source-20261119/`。
