# 潘小兜老卤小作坊：产品完善评估

评估日期：2026-11-18。依据为当前工作区（含未提交修改）的 README、数据库结构、5 个小程序页面及全部后端控制器。

本次完成代码与流程核对、后端 TypeScript 类型检查、小程序 JavaScript 语法检查，以及使用内存模拟数据的关键场景验证；未连接生产数据库、未操作线上订单、未进行微信真机或真实支付验证。文中“已实现”表示代码存在，不能替代线上验收。

## 1. 产品定位与当前阶段

这是服务临安锦城周边居民的单店卤味预订小程序，经营特点是小批量现做、店主自送、到店自提，通过会员与熟人推荐促进复购。

当前具备产品雏形：顾客可以选菜、计算会员价及积分抵扣、创建订单、查看订单状态；掌柜可以维护菜品、修改部分运营参数、操作发车、维护会员及人工调整积分。技术栈为微信原生小程序、Koa/TypeScript、MySQL、微信云托管。

判断：已经搭好了页面与业务骨架，但交易、履约和账户规则尚未形成可靠的营业闭环。下一阶段应围绕“买得明白、付得真实、按时拿到、出问题能处理、掌柜忙时也能管”完善。

推荐主流程：

> 确认营业与可选批次 → 选择菜品和规格 → 确认自送范围或自提 → 核对价格 → 支付 → 掌柜接单备餐 → 配送或核销自提 → 完成 → 积分返利结算 → 再次购买。

## 2. P0：正式接收真实付费订单前补齐

### P0-01 真实支付、退款与订单资金状态

- **现状**：首页和订单页通过弹窗确认后请求 `/api/order/pay-success`；没有调用 `wx.requestPayment`。后端该接口直接将订单从 10 改为 20 并发积分、返利，没有微信交易凭据校验，也没有订单归属校验。取消订单仅修改数据库状态、退回积分，没有微信退款调用。
- **业务影响**：顾客未实际付款，系统也可能显示支付成功；页面承诺“原路退款”，实际未发生资金退款。
- **完善范围**：微信支付下单、支付通知验签与金额校验、主动查单补偿、支付幂等、退款申请及结果确认、异常订单查询。支付入口需校验身份与订单归属，支付完成以可信支付结果为准；零元订单另设内部结算分支。
- **验收**：支付取消不能成为已支付；重复通知只入账一次；网络中断后能恢复正确状态；退款完成前显示“退款中”；现金、积分、返利与支付流水可核对。
- **证据**：`miniprogram/pages/index/index.js:556`、`miniprogram/pages/order/order.js:60`、`server/src/controllers/order.ts:261`、`:343`。

### P0-02 掌柜身份与后台权限

- **现状**：公开配置接口返回全部配置，包含 `ADMIN_PASSCODE`；知道口令即可通过验证接口将自己的微信账号提升为管理员。前端还硬编码口令并将本地标记当作后台入口凭据。后端管理接口虽有权限检查，但管理员授予过程存在问题。
- **业务影响**：菜品价格、会员资产、运营参数、顾客地址和手机号可能被非掌柜操作或查看。
- **完善范围**：公开配置采用白名单；掌柜通过受控账号绑定或管理员授权开通；支持撤销权限；前端以服务端权限结果为准；记录敏感操作人、对象和时间。生产环境移除面向本地联调的 query openid 回退，并确认云托管入口的可信身份边界。
- **验收**：普通用户无法读取口令、无法自行提权；权限撤销后旧设备立即失效；手机号、地址和积分调整仅授权角色可访问。
- **证据**：`server/src/controllers/admin.ts:8`、`server/src/controllers/user.ts:120`、`miniprogram/pages/member/member.js:210`、`server/src/middlewares/auth.ts:26`。

### P0-03 完整订单列表与合法状态流转

- **现状**：订单页用 `find` 只取一笔进行中订单，其余未完成订单不出现在历史列表；确认完成接口未限制订单原状态；取消未付款与已退款共用状态 50；下单无请求幂等键，未付款订单没有自动关闭与积分释放机制。
- **业务影响**：连续下两单后，较早订单可能暂时“消失”；待付款订单可被接口直接改成已完成；放弃支付后积分持续被占用。
- **完善范围**：全部/待付款/待备餐/待配送或待自提/已完成/已取消/售后筛选、订单详情、支付倒计时、自动关单释放权益、重复提交防护；区分交易状态、履约状态、退款状态并限定合法转换。
- **验收**：同时存在两笔以上进行中订单时均可查看和操作；未付款或已取消订单不能确认收货；支付通知与超时关单竞争时最终结果正确。
- **证据**：`miniprogram/pages/order/order.js:41`、`server/src/controllers/order.ts:153`、`:460`。

### P0-04 批次、营业时间与履约分流

- **现状**：页面写“每日两炉”，代码主要按固定 16:30 判断今日/明日；订单预约仅存文案。批量发车更新所有状态 20 的订单，没有按配送方式、日期、批次过滤。自提码虽然已生成，但没有掌柜输入/扫码核销流程。
- **业务影响**：明日预约、自提订单可能一起进入“配送中”；掌柜难以判断今天该做哪些、哪些已经取走。
- **完善范围**：先明确实际是一炉还是两炉；以日期和批次 ID 存储预约，配置截单、备餐、可取餐/配送时间、容量和休息日；自送与自提分别操作。自提支持在当前有效订单范围内校验取货码、核对手机号并确认取餐。
- **验收**：今日自送发车不影响明日或自提订单；截单后不能选过期批次；自提码只可核销一次，未支付订单不可核销。
- **证据**：`miniprogram/pages/index/index.js:195`、`server/src/controllers/order.ts:432`、`miniprogram/pages/admin/admin.js:148`、`miniprogram/pages/order/order.wxml:54`。

### P0-05 真实联系人和可配送范围

- **现状**：首页预填固定联系人、手机号、地址；支持微信地址选择及弹窗输入，但下单没有完整服务端校验。数据库有最大配送距离配置，业务代码未应用。
- **业务影响**：顾客可能直接用示例地址付款；超出掌柜配送能力的订单也能生成。
- **完善范围**：移除默认示例信息；分别收集联系人、手机号、详细地址；保留上次有效地址；首版可采用可维护的小区白名单，或地图定位及范围校验；超范围引导自提。自提也须确认有效联系电话。
- **验收**：缺少必填信息、错误手机号、超范围自送均在付款前拦截，绕过前端请求也无法下单。
- **证据**：`miniprogram/pages/index/index.js:113`、`:404`、`server/src/controllers/order.ts:193`、`init.sql:31`。

### P0-06 售罄校验与每日可售数量

- **现状**：前端禁止添加售罄商品，但服务端算价不检查 `status` 和 `stock_qty`；库存字段未参与扣减。不存在的商品会被静默忽略。
- **业务影响**：已经放入购物车的商品售罄后仍能下单；最后几份可能超卖；失效购物车可能生成不完整甚至无商品订单。
- **完善范围**：维护每日或批次可售份数；下单校验并原子预占，付款后确认消耗，取消或超时释放；商品下架、删除、变价时提示顾客重新确认；数量必须为限定范围内的正整数。
- **验收**：最后 1 份并发购买最多成功 1 单；全部商品失效时拒绝下单；顾客清楚看到需要调整的菜品。
- **证据**：`server/src/controllers/order.ts:39`、`:163`、`init.sql:55`。

### P0-07 会员、积分和返利规则闭环

- **现状**：免费开通会员接口不检查是否配置为 FREE；推荐绑定未实际要求推荐人是会员；支付时返利不检查推荐人当前资格。退出会员清空红包，但退出确认文案未明确这一后果；累计消费仍保留，之后付款可能再次自动入会。返利在支付时立即到账，而确认收货文案说收货后结算。
- **业务影响**：入会门槛可被绕过、退出后仍可能获返利或再次入会；资产清零及到账时间引发争议。
- **完善范围**：统一入会资格、升级时点、退款后是否保留资格、主动退出后的再入会方式、推荐人资格和绑定窗口。返利建议“支付后待结算、履约完成后可用”；退款冲正不能简单把余额扣到零后忽略未追回部分。建立完整积分/红包流水，退款、消费、赠送、退出均可追溯。
- **验收**：非 FREE 模式不能免费激活；不符合资格的推荐人不能获返利；退出前明确提示红包处理；退款后账户账实一致，已消费的奖励有明确追回规则。
- **证据**：`server/src/controllers/user.ts:152`、`:203`、`:225`、`server/src/controllers/order.ts:297`、`:308`、`:404`、`miniprogram/pages/member/member.js:128`、`miniprogram/pages/order/order.js:157`。

### P0-08 算价、配置和前台承诺一致

- **现状**：商品实际采用独立会员价，未统一按 8.8 折计算，例如 48 元商品会员价 42 元；会员门槛、折扣、返利率、地址、电话、批次等多处写死。公告可在后台保存，但首页未读取。积分按订单现金实付取整发放，商品卡却按会员单价展示积分，口径不一致。普通积分与红包叠加没有按剩余货款限制扣减。
- **业务影响**：掌柜“设置成功”，顾客却仍看到旧规则；优惠承诺与实际金额不同；权益可能多扣。
- **完善范围**：选择“统一折扣”或“逐商品会员价”之一作为对外规则；明确免运门槛按折前、折后还是抵扣后金额计算，是否包含配送费计积分/升级消费。所有页面读取同一份公开业务规则；提交前试算失败应阻止支付，最终价格变化需重新确认；后台校验参数范围并正确反馈业务失败。
- **验收**：修改公告、会员门槛及返利比例后相关页面一致生效；两类抵扣合计不超过货款，不抵运费；试算、下单、详情与资产流水一致。
- **证据**：`server/src/controllers/order.ts:62`、`:291`、`server/src/controllers/product.ts:28`、`miniprogram/pages/index/index.wxml:49`、`miniprogram/pages/admin/admin.js:388`。

## 4. P2：有真实订单数据后优化复购与利润

1. **再来一单与常买清单**：从历史订单快速加购，自动提示失效/售罄商品及价格变化。先减少老客点餐步骤。
2. **小规模套餐试验**：双人餐、下酒组合、荤素拼盘；观察客单价和毛利，避免只以折扣拉高订单量。
3. **轻量会员触达**：生日礼、长期未复购提醒、常客回馈，先明确触达授权与频率；不要一开始叠加复杂等级与优惠券规则。
4. **口碑与推荐效果**：收集口味评价和服务反馈；跟踪邀请用户首单与复购，而非只看绑定人数。
5. **备货与损耗**：按批次记录售出、剩余、报损，结合近几周销量辅助准备份数；有稳定销量后再考虑预测。
6. **经营收益分析**：计入原料、包装、支付成本、自送成本、折扣及权益成本，评估会员与推荐机制是否带来增量利润。

会员折扣、普通积分和推荐返利需要一起看成本。例如按统一 8.8 折假设，原价100元的商品现金实付88元时，3%推荐奖励为2.64元，88普通积分的名义兑换价值为4.40元，优惠及后续权益合计名义价值19.04元，尚未计入配送等成本。这不是实际即时支出或利润率，但说明“只看3%返利”不足以判断经营收益。

## 5. 分阶段推进建议

| 阶段 | 交付重点 | 进入下一阶段的条件 |
| --- | --- | --- |
| A：交易与权限闭环 | 真实支付退款、受控管理员授权、订单状态和账户流水、全部订单可见 | 资金和订单可核对；重复回调、支付失败和退款异常均可恢复 |
| B：真实履约试营业 | 日期批次、自送范围、每日份数、自提核销、必填联系人、真实规则配置 | 今日/明日、自送/自提互不串单；并发末份不超卖 |
| C：掌柜效率与顾客体验 | 工作台、备餐汇总、新单提醒、商品详情、售后、真实分享海报 | 掌柜能独立处理完整营业日；顾客不用反复电话问进度 |
| D：增长与利润优化 | 再来一单、套餐、小规模回访、数据统计、毛利与损耗 | 通过真实订单评估复购和净收益，再决定加哪些运营功能 |

上述是依赖顺序，不是工期承诺。A、B 阶段完成后再扩大推广；试营业前也应补齐必要的门店信息和用户规则告知。

上线准备另需检查环境隔离、数据库备份恢复、非破坏性结构迁移、支付/订单异常告警和发布回滚。当前 `init.sql` 是含 DROP TABLE 的重建脚本，不能作为已有营业数据环境的常规升级方式；README 的支付退款与动态配置等描述也应更新为经过验收的真实能力。

## 6. 建议跟踪的经营指标

- **成交漏斗**：访问菜单 → 加购 → 进入结算 → 创建订单 → 真实支付成功；先找顾客在哪一步退出。
- **履约质量**：按预约时段完成比例、超卖/缺货订单、错漏品、未核销自提、超时及退款原因。
- **复购**：首购用户7日/30日复购、会员与非会员复购、推荐用户的有效首单及后续消费。
- **经营收益**：净实收、客单价、商品毛利、自送成本、权益发放/核销、红包未核销余额、报损。
- **统计口径**：有效订单按支付、履约、退款情况定义，不能简单以状态数值大小判断；现金收入、商品销售额、积分抵扣和退款分别记录，避免重复扣减权益成本。
